# CPG availability — enumeration-first guidance

The CPG MCP tools (`paths`, `reachable`, `callers`, `callees`, `xref`,
`func`, `inspect`, `entrypoints`) are your **primary enumeration**
tools for this anchor. CPG indexes call nodes that shell grep can
miss — aliased imports (`from x import y as z`), decorator stacks,
dynamic dispatch, generated code. Use CPG to find sinks; use shell to
read what's there.

**Standard opening sequence on any anchor:**

1. `entrypoints(file=<anchor>)` — every routed handler in the anchor
   file. Surfaces handler-shape directly and tells you what auth
   gates each handler claims via decorator metadata.
2. `xref(symbol=<call>)` for each dangerous call in the language
   module's bug-class list. Joern stores call nodes by short name
   (`eval`, `execute`, `loads`, `get_or_create`, `set_password`,
   `setattr`), so search the unqualified function name. When the
   language module ships a CPG-query battery, run it before
   committing to a verdict.
3. For each hit `xref` returned, `inspect(location=<file:line>)`
   to see the AST shape and surrounding code without paging the
   whole file via shell.

**Walking a candidate sink:**

- `reachable(sink=<file:line>, sources_hint=<framework-pattern>)`
  to confirm an attacker-controlled source actually reaches the
  sink. A sink with no reachable source is non-boundary.
- `paths(src=<source>, dst=<sink>)` for the source-to-sink walk
  you'll cite as evidence in the final report.
- `callers(symbol=<call>)` / `callees(symbol=<call>)` when sketching
  call structure, or when `reachable`/`paths` came back empty — the
  symbol may be CPG-blind (function pointer, C-extension, dynamic
  attribute), and the right pivot is `xref` on a related symbol.

**Path convention.** CPG stores repo-relative paths. Expect
`src/foo.py:42`, not `/workspace/src/foo.py:42`. When you cite a
location in your final report, prefer the repo-relative form CPG
returned (it matches the human reviewer's working-copy layout).

**Handler-shape sanity check.** When the anchor matches handler shape
(≥3 routed-handler matches in its first 200 lines — `def <name>(request, ...)`,
`class <Name>(View|...)`, `@app.<verb>`, `@<verb>Mapping`,
`func <Name>(c *gin.Context)`, `@RestController`, etc.) AND the
framework hints name a web framework, you MUST run the full CPG
enumeration battery from the language module **before any
`final_output`** — not just before no-finding. Surfacing one finding
does not release you from enumerating other sink categories on the
same file. The canonical false negative is the second finding that
lived in a different category from the first and got missed because
`final_output` landed too early.

**Cover your whole scope, one item at a time.** Your scope is the

## Sink categories

The nine canonical categories:

`shell` (command construction) · `sql` (query construction) · `fs` (path / file I/O) · `url` (URL/HTTP construction, SSRF) · `deserialization` (pickle/yaml/marshal/etc.) · `template` (template injection) · `authorization` (access control, auth/authz) · `crypto` (cipher / hash / nonce / key handling) · `logging` (log injection, secret leakage)

Every surviving sink lands in exactly one of these. Concurrency, TOCTOU, and resource-limit issues surface through the relevant category (e.g., race conditions in path handling appear as `fs`).

## C/C++-specific review

Memory-safety bugs are the threat model. Look for unsafe string/buffer operations, integer wraps in allocation, format strings, command injection, path traversal, and concurrency races.

### Common C/C++ bug patterns

**Memory corruption:**
- Unbounded writes: `strcpy`, `strcat`, `sprintf`, `gets`, `scanf("%s")` on user input (CWE-120, CWE-787).
- `memcpy(dst, src, len)` where `len` from input not bounded vs `sizeof(dst)` (CWE-787).
- Off-by-one on loop bounds (`<=` vs `<`) on fixed buffers (CWE-193).
- Return stack pointers (CWE-562). Use-after-free: `string_view` outliving owner, `unique_ptr::get()` held past `reset()` (CWE-416).

**Integer bugs:**
- Size wrap in allocation: `int len = user; malloc(len + header)` where addition overflows (CWE-190).
- `size_t` truncated to `int` (CWE-197). Negative size as unsigned (CWE-681).

**Other high-value issues:**
- Format strings: `printf(user_input)` not `printf("%s", user_input)` (CWE-134).
- Command exec: `system(cmd)`, `popen(cmd)` with constructed strings (CWE-78). `execv`/`execve` safer.
- Path traversal: `fopen(user_path)`, `ifstream(user_path)` need `realpath()` + prefix check (CWE-22).
- Deserialization: custom binary parsers reading sizes then allocating without bounds (CWE-502).
- Race conditions: unsynchronized access to shared globals, no `mutex`/atomics (CWE-362). TOCTOU: `stat()` then `open()` on user path (CWE-367).
- Iterator invalidation: mutate container while iterating, erase during for-each (CWE-416).
- Exception in destructor → `std::terminate` (DOS).
- OpenSSL: unchecked `EVP_*` returns, static IVs, raw ECB mode (CWE-327, CWE-330).
- Scientific libraries (ROOT, HepMC, MPI, CUDA, HDF5): dimension/size reads from input used to allocate unchecked.

### Skip reporting

- Modern C++ ownership in use (`unique_ptr`, `shared_ptr`, `vector`) — real bugs need specific bad constructs.
- `std::string`/`string_view` in use — focus on C APIs crossing boundaries.
- AddressSanitizer in CI/CMake (`-fsanitize=address`) — real bugs would be caught.
- `std::filesystem::path` — safer but NOT traversal-proof without `canonical()` + prefix check.
- Fuzzing coverage — un-fuzzed parsers higher-value than fuzzed surface.
- Missing `noexcept`, style choices, `reinterpret_cast` between compatible types (e.g. `char*` ↔ `uint8_t*`), C++ version suggestions.

### Red flags

- C-string APIs on user data (CWE-120).
- `reinterpret_cast` of network bytes to struct (CWE-843, CWE-125).
- `malloc(user_size * user_count)` or `new T[user_n]` (CWE-190 → CWE-787).
- Manual resource cleanup without exception safety (CWE-404).
- `#pragma pack` + network deserialization (CWE-125).
- Use-after-move: `std::move(x); use(x);` (implementation-defined bug).
- Custom crypto vs OpenSSL/libsodium.
- `system()`/`popen()` in handler paths.
- Missing bounds on array indices tied to user input.

### CPG usage patterns — C/C++

**Starting investigation:** for each sink class (`curl_easy_setopt`,
`memcpy`, `strcpy`, `open`, `fopen`, `system`, `popen`, `sprintf`, etc.),
`xref(name)` to locate all occurrences, then investigate case by case.

**Key patterns:**
- SSRF via parsed response — `paths(src="curl_easy_perform", dst="curl_easy_setopt")` to see if a parsed-response field flows into a second URL.
- Buffer overflow — `reachable(sink="file.cpp:LINE")` on each `memcpy`/`strcpy` site; if argv/env/fread reaches the copy with no size-check hop, the finding is real.
- Large function body — call `func(name)` first; if `numCallees` is small, read directly; if large, use `callees` to narrow to the dangerous-sink subtree.
- Defense verification — `paths(src=<plausible_source>, dst=<sink>)` before marking `present-and-effective`; empty = defense likely works; non-empty = read hops and identify what breaks the attack.
